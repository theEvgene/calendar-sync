# HANDOFF — Calendar Sync v1.2, этап A

Проект самодостаточен: SPECIFICATION.md содержит полную исходную спецификацию.
Ядро не импортирует COM, Google SDK или адаптеры. Event содержит только необходимые
поля; исходный ID обязан устойчиво обозначать экземпляр, включая перенесённый.
FakeAdapter проверяет алгоритм; GoogleAdapter и OutlookAdapter реализуют тот же
контракт. Код реальных адаптеров требует приёмки на целевом ПК.

## Контракт и восстановление

`read(start, end)` возвращает развёрнутые экземпляры, пересекающие полуоткрытое окно.
`complete=True` означает успешно прочитанные ВСЕ страницы/экземпляры. Исключение не
является пустым снимком. Отсутствие ранее известного будущего экземпляра в полном
снимке означает отмену/удаление/выход за окно. Все эти случаи требуют удалить его
связанную будущую копию. Прошедшие по сохранённому исходному end связи сохраняются.
Явные declined/cancelled не входят в желаемое состояние. Исключения повторений
разворачиваются адаптерами, а не отдельным RRULE-движком в ядре.

`copies()` возвращает полную инвентаризацию маркированных копий без временного
ограничения. Google хранит private extendedProperties `calendarSyncOwner=v12` и
`calendarSyncKey`; Outlook — UserProperty `CalendarSyncKey`. Только эти маркеры
позволяют опознать копию. Исходный ключ — SHA-256 JSON [направление, календарь, ID].
SQLite хранит ключ/направление/ID копии/исходный end; UNIQUE PRIMARY KEY запрещает
две локальные связи одного ключа. Дубли маркеров блокируют направление, их нельзя
автоматически удалять, выбирая случайную копию.

После создания перед SQLite возможен crash: новый снимок обнаруживает маркер и
восстанавливает связь без повторного create. При потере SQLite состояние строится
из полного инвентаря; неизвестные устаревшие маркеры сохраняются. Это сознательная
защита: без исходной связи невозможно доказать, что копию допустимо удалить.
Повреждённая БД блокирует запуск. Неполный инвентарь блокирует запись. Не удаляйте
маркеры вручную: после потери маркеров безопасная автоматическая идентификация
невозможна. Параллельная запись с другого ПК этим локальным lock не предотвращается.

Google использует детерминированную цепочку ID при insert: подтверждённые tombstone
ID пропускаются, активный ID после ambiguous timeout сверяется по маркеру. Это
позволяет воссоздать вручную удалённую копию и не дублировать ambiguous insert.
COM перепроверяет полный инвентарь перед повторным create; реальную видимость Save
и последствия COM timeout необходимо проверить на этапе B.

## Что проверять на этапе B

1. Получите разрешение корпоративной политики на Body → личный Google с visibility
   default. Перенесите только чистый пакет. Настройте локальный токен, ID, timezone,
   оставив расписание выключенным. `diagnose` должен работать без подключения.
2. Read-only проверка: default Outlook folder, разворот серии, исключения и отмены,
   `GlobalAppointmentID`, OriginalDate, StartUTC/EndUTC, All-day и DST. COM Restrict
   использует строку даты US-формата: проверьте локаль Outlook. Ошибки чтения должны
   блокировать удаления, а не возвращать пустой complete-снимок.
3. Создайте вручную только разрешённые синтетические события. Локально получите их
   нормализованные ID. Проверьте Body (обычный текст), оба Google-источника, Busy,
   privacy, напоминания и отсутствие рассылок. Выполните dry-run с --test-id.
4. Разрешите только тестовые записи (--test-id): create/update/delete, declined,
   series move/exception/cancel, All-day, ручное удаление копии, crash/restart,
   потеря SQLite, полный инвентарь и отсутствие обратных циклов. Три неизменённых
   последовательных apply должны дать ноль CREATE/UPDATE/DELETE.
5. Возвращайте разработчику только обезличенные ошибки и синтетические примеры.
   Если COM-код нуждается в коррекции, добавьте mock-регрессию и обновите документы.
6. Новый полный dry-run, разбор удалений и явное подтверждение заполнения; только
   после успешной реальной приёмки выставьте stage_b_accepted и включайте расписание
   по README. Не объявляйте production-ready до завершения этой последовательности.

## Границы проверки этапа A

Проверка на Python 3.13.2, а не указанном в спецификации целевом 3.13.14.
Реальные COM, Outlook timezone/locale/recurrence semantics, права записи,
Google OAuth/scopes, propagation/consistency и реальная сеть НЕ проверялись.
Нормализованные повторения проверяются mock-экземплярами; это не доказательство
корректности конкретного COM-профиля. tzdata закреплена ради воспроизводимости;
перед эксплуатацией согласуйте актуальные правила часовых поясов и зависимости.
Google exception-коды 408/429/5xx, TimeoutError/ConnectionError и известные busy/RPC
COM HRESULT повторяются до 3 раз с backoff 1/2 секунды. Остальные ошибки дают
ненулевой результат события/направления, не раскрывая provider error body в журнал.

Автоматические тесты и проверка переносимости запускаются командами из README.
Отдельный фактический результат проверки сохранён в VALIDATION.md.
